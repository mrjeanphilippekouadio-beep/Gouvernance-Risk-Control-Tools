## 3. Findings

### F-PNL3-01 : MAJOR : « Approuver » ne peut jamais réussir (confirme A10)
Reproduction (vrai backend) : A demande l'assouplissement (202), B ouvre l'écran, clique Approuver. L'écran envoie `{}` ; le serveur répond 400 « Requête invalide. » ; la demande reste PENDING. Même message pour l'auteur qui s'approuve lui-même : le refus maker-checker est masqué par le 400 de forme. Tests : `QA-retest2.test.ts` (`it.fails` sur le client), Playwright. Correctif : champ de motif dans l'écran, `reason` dans le corps.

### F-PNL3-02 : MAJOR : un retour à la ligne dans un motif donne un 400 sans explication (confirme A10, portée plus large)
Cause : `reasonText(max)` est monoligne par défaut ; toutes les zones de saisie de motif de l'application sont des `<textarea>`. Avant le lot, ces corps acceptaient le retour à la ligne : régression. **19 routes** refusent un motif sur deux lignes (archivage contrôle/département/processus/KPI/risque/appétence, désactivation KRI/grille, bascule de module, Dispositif : abandon, demande d'activation, identité ; les 7 PUT/POST de `config` ; rejet de demande de mode) et le dialogue de double confirmation (D4, préexistant mais manqué au passage précédent). Témoins : retrait de demande, rejet et refus du Dispositif acceptent le multiligne. Le message affiché est le générique « Requête invalide. » : l'utilisateur ne peut pas deviner. Vu au navigateur sur 5 écrans du lot F3. Correctif : `multiline = true` pour tous les motifs saisis en zone de texte (le test de garde `retestLot` se contente du helper). Tests : 19 `it.fails` + un témoin du message.

### F-PNL3-03 : MAJOR : trois cartes de « Réglages de gouvernance » échouent toujours (non vu par A10)
Mode d'évaluation par défaut, Seuils de passage au Comité, Passage obligatoire par le Comité : `ConfigService` appelle `assertNotOwnedByFramework()` dès que le Dispositif est câblé (c'est le cas dans `server.ts`). Reproduit sur le vrai backend, motif valide : 400 « Ce réglage est porté par le Dispositif : créez une nouvelle version ». L'écran offre pourtant « Modifier » et l'intitulé « Chaque changement exige un motif », sans signaler que ces réglages ne s'éditent plus ici ; il lit même ces valeurs depuis `GET /config`. Seules la politique d'auto-validation et le cumul Comité/Audit sont écrivables. Conséquence secondaire : les correctifs F-PNL2-06 sur l'application et l'audit de `committee-enforcement` ne sont atteignables que pour le cumul. Correctif : retirer ou rendre en lecture seule ces cartes avec renvoi vers le Dispositif, ou lire la valeur de la version applicable.

### F-PNL3-04 : MINOR : le client perd le `code` du 409 (confirme A10, sans effet aujourd'hui)
Le serveur met `code` à la racine ; `ApiError` lit `payload.error.code`. Le dialogue de double confirmation fonctionne parce que le préfixe `GOVERNANCE_CONFIRMATION_REQUIRED:` du message est repris (vérifié au navigateur : 409 puis dialogue puis 200, corps renvoyé `{ rule, reason }`). Fragile : retirer le préfixe casse le dialogue.

### F-PNL3-05 : MINOR : statut `APPLIED` côté serveur, `APPROVED` côté client (confirme A10)
`PolicyRequestStatus` du client ne contient pas `APPLIED`. Sans effet visible : l'écran n'affiche que la demande en attente.

### F-PNL3-06 : INFO : l'écran des demandes de mode exige un processus
Pas de liste globale (besoin backend déjà noté par le développeur). Parcours réel vérifié : proposer (201), valider seul (409, dialogue, confirmation, 200), demande VALIDATED, `validationIndependence = WITHOUT_INDEPENDENT_REVIEW`, badge affiché.

### F-PNL3-07 : INFO : hygiène
Le test `retestLot-pg` 074 est sensible à la charge (A10) ; `QA-retest2` utilise des attentes fixes de 120 à 200 ms pour l'écriture asynchrone du `lastSeen` : même fragilité possible sous charge, relancer avant d'y voir un défaut.
