## 2. Valeur probante du journal

### SEC-q251-01 — Un renommage n'est plus prouvé, et la lecture réétiquette le passé (LOW, CVSS 2,4)

- **Preuve (PoC vitest, non commité)** : `create(displayName "Alice Martin")` puis `update(displayName "Bob Durand")`.
  - ligne `UPDATE` : `JSON(oldValue) === JSON(newValue)` donne **`true`**. Le journal enregistre une modification « vide ».
  - `listRecent` : la ligne `CREATE` est restituée avec `entityDisplayName = "Bob Durand"`, pas le nom au moment de la création.
- **Étendue** : un seul chemin applicatif modifie `display_name` : `UserService.update` (droit `user.update`, administrateur). L'e-mail n'est modifiable par aucun chemin applicatif (seulement à la création). Toute modification SQL directe était déjà hors journal. Le nom de l'auteur (`userDisplayName`) était absent de toutes les lignes non `User` avant ce lot : là, on n'a rien perdu, on a ajouté un nom **courant**.
- **Scénario** : un administrateur renomme le compte X avec le nom d'une autre personne ou un nom trompeur. Toutes les actions passées de X apparaissent sous ce nom. Le journal ne montre ni l'ancien nom ni même le fait du renommage (la ligne `UPDATE` ne diffère pas). L'id reste exact, donc l'attribution technique est intacte. Seule la lecture humaine est trompée.
- **CVSS 3.1** : `AV:N/AC:L/PR:H/UI:R/S:U/C:N/I:L/A:N` = **2,4**.
- **Lien avec q250 A** : la jointure à la lecture est précisément ce qui rendra la pseudonymisation (q250) applicable en un seul endroit. Garder l'ancien nom dans le journal irait contre q251 A. Le correctif ne doit donc **pas** recopier de valeur.
- **Correctif proposé (le plus simple, compatible DECISION-120)**, A06 :
  1. dans `UserService.update`, si `before.displayName !== after.displayName`, ajouter `displayNameChanged: true` à `newValue` (aucune valeur, ni ancienne ni nouvelle). Même chose pour `emailChanged` le jour où l'e-mail deviendra modifiable ;
  2. à l'écran, présenter le nom joint comme **nom actuel** (libellé ou info-bulle), l'id restant affiché. L'API peut le refléter par le nom du champ (`userCurrentDisplayName`) si le front n'est pas encore branché. C'est le cas : `AuditLogPage` n'affiche que `userId`, le changement de nom est donc gratuit.
- **Test de régression** : renommer, puis vérifier `newValue.displayNameChanged === true` et l'absence des deux noms dans le dump ; mettre à jour seulement `departmentId` et vérifier l'absence du drapeau.
- **Résidu accepté si le correctif est appliqué** : on sait **qu'un** renommage a eu lieu, **quand** et **par qui**, pas **de quoi vers quoi**. C'est la conséquence voulue de q251 A. Décision PO seulement si l'audit veut l'ancien nom (voir « Décisions PO »).

### SEC-q251-02 — Champs métier en texte libre porteurs de nom ou d'e-mail encore journalisés (INFO, pas de CVSS)

Ce n'est pas une vulnérabilité : la donnée est déjà lisible dans l'entité par ceux qui ont `department.read`, `process.read` ou `kpi.read`. C'est un **écart de périmètre** avec la formule « le journal n'écrit plus nom ni e-mail ». Ces valeurs échapperont aussi à la pseudonymisation q250, qui n'agira que sur `users`. Le test ajouté par le lot ne contrôle que les lignes `entityType = "User"`, ce qui ne garde pas contre ce cas. **À trancher par Privacy (A15) et le PO** (voir plus bas). Piste technique si la réponse est oui : migrer ces champs vers un id de compte (comme `Risk.ownerId`), pas masquer au journal.

### SEC-q251-03 — Jointure non groupée (INFO)

Recommandation de durcissement non bloquante : un `getByIds(tenantId, ids[])` (une requête `= ANY($2)`) au lieu de N `getById` en parallèle.

### SEC-q251-04 — `Control.validator` reste journalisé (INFO, pas de CVSS)

`Control.validator` (`text`, libellé « Validateur » à l'écran, saisie libre) est de même nature que `executor`, mais n'est pas dans `CONTROL_PERSON_FIELDS` : sa valeur reste copiée dans les lignes `Control` (CREATE/UPDATE/DELETE). Dans le legacy, les deux colonnes sont des **rôles** (« Rôle exécuteur », « Rôle valideur »), pas des personnes. Le choix du PO sur `executor` (q273) et le traitement de `validator` sont donc incohérents. Correctif trivial si le PO le confirme : ajouter `"validator"` à `CONTROL_PERSON_FIELDS`. Sinon, documenter que ces deux champs portent un rôle. Ce n'est pas une exposition (lisible par `control.read`), mais c'est une copie qui échappera à q250.
