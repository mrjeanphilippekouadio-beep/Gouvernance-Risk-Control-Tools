## Constats

### SEC-093-01 : le trigger d'audit ne voit pas une liaison posée directement (NULL → valeur) et n'enregistre pas l'exécutant

- Gravité : **LOW 2,7** (`CVSS:3.1/AV:N/AC:L/PR:H/UI:N/S:U/C:N/I:L/A:N`), traçabilité.
- Confiance : CONFIRMED. Sous runtime, `UPDATE users SET identity_provider='google', identity_subject='ATTACKER'` sur un compte non lié n'écrit **aucune** ligne. La condition `WHEN (OLD.identity_subject IS NOT NULL …)` exclut ce cas, pour ne pas doublonner la ligne que l'application écrit à la première connexion.
- Impact limité : depuis q285, lier à l'avance un compte d'un domaine d'entreprise à un identifiant étranger ne permet pas d'usurper (il faudrait un jeton attestant ce domaine avec cet identifiant), mais cela bloque la vraie personne sans aucune trace. Il faut de toute façon les droits SQL du runtime ou du propriétaire.
- Correctif proposé (A07) : faire porter **toute** la traçabilité par le trigger. L'application pose `SET LOCAL grc.identity_binding = 'first-login'` dans sa transaction ; le trigger se déclenche sur tout changement, y compris NULL → valeur, et écrit « première connexion » si le réglage est présent, « changement direct en base » sinon. L'`INSERT` d'audit de `ensureIdentityBinding` est alors retiré. Ajouter aussi `session_user` (et éventuellement `inet_client_addr()`) dans `new_value` : un DevOps se connecte avec un autre rôle que l'application, ce qui suffit à distinguer les deux.

### SEC-093-02 (INFO) : 093 échoue s'il existe déjà une décision SOLE_RM avec le drapeau à false

- Des décisions SOLE_RM prises entre le déploiement de 089 et celui de 090 portent `sole_rm_at_request = false` (valeur par défaut de 090). `ADD CONSTRAINT` vérifie les lignes existantes : 093 échoue alors et s'annule entièrement. C'est un échec fermé ; je l'ai reproduit (« check constraint … sole_rm_shape … », puis ROLLBACK).
- Avant de déployer sur staging et en production : `SELECT count(*) FROM risk_framework_change_requests WHERE decision_regime = 'SOLE_RM' AND NOT sole_rm_at_request;`. Si le résultat est supérieur à 0, ne pas réécrire ces décisions : poser le CHECK en `NOT VALID`, ce qui couvre les nouvelles lignes seulement, et le documenter.

### Question d'A06 : la garde INSERT de 057 ne contrôle pas `sole_rm_at_request`

**Réponse : INFO, pas une question pour le PO, et je ne recommande pas de le fermer maintenant.**

- C'est confirmé : sous runtime, une demande PENDING peut être insérée avec le drapeau à `true` ; la décision SOLE_RM passe ensuite au niveau SQL, puisque la vérification « encore seul Risk Manager maintenant » est dans le dépôt, pas en base.
- Mais c'est la même classe que la falsification d'une approbation sous runtime, déjà notée (voir 056 et B-6c) : avec les droits SQL du runtime, on peut déjà écrire une décision NORMAL au nom d'un autre Risk Manager du tenant. Fermer ce seul drapeau n'enlève donc aucune capacité à l'attaquant. Cela obligerait en plus à recopier en SQL la définition de « Risk Manager actif » (groupe fixe, `user_roles` non révoqués, comptes non supprimés ni suspendus), avec un risque de divergence avec `readBootstrapFacts`.
- Il n'y a pas d'arbitrage métier, donc pas de question au PO. Si un jour on traite la falsification sous runtime en général (décision dérivée d'un contrôle en base du décideur), on l'inclura à ce moment-là.
