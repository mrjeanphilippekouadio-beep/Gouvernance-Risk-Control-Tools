**SET_DEFAULT**
- Demande : `riskframework.update` + groupe RM ; autre tenant = 403. Le demandeur ne peut pas approuver (403) ; `sole-confirm` refusé (400, SOLE_RM limité à ASSIGN_PROCESS) ; non-RM = 403.
- Approbation par un tiers : ancien défaut à false puis nouveau à true dans la même transaction, audit avant/après des deux Dispositifs + APPROVE, le tout dans la transaction ; rejouer = 409.
- Concurrence : deux demandes sur deux Dispositifs approuvées en parallèle (×2 chacune) = 2 × 200 + 2 × 409, **toujours un seul défaut** (verrou des deux lignes par ordre d'id + index unique).
- La règle d'approbation est relue sous verrou (`FOR SHARE` sur la version ACTIVE) : 409 si elle a changé.

**Archivage**
- Défaut = 400 ; processus vivant rattaché = 400 ; demande en attente = 409 ; motif vide = 400 ; non-RM avec `riskframework.archive` = 403 ; autre tenant = 403 ; `PATCH` générique avec `archivedAt` = 400. Permission dédiée `riskframework.archive`, jamais `update` : règle des actions terminales respectée.
- Succès : Dispositif et versions archivés, échelle passée en ARCHIVED seulement si plus aucune version ACTIVE ne la référence, audit STATUS_CHANGE avec motif dans la transaction. Ensuite : ré-archivage, demande de défaut et rattachement = 400.
- Verrous et ordre de lecture (point signalé par A06) : le Dispositif est verrouillé `FOR UPDATE` avant la lecture des processus et des demandes. Une décision ASSIGN_PROCESS concurrente tient le Dispositif en `FOR SHARE` (sérialisée, puis relit `archived_at`) ; une nouvelle demande prend un `KEY SHARE` par la clé étrangère `framework_id`, donc l'archivage l'attend puis la voit (PoC R1 : soumission tenue ouverte, archivage = 409, rien d'archivé). La garde 091 rejoue la condition « aucun processus vivant » en base.

## Constats

### SEC-B13-01 — INFO (A07)
R-02 n'est vérifié que si la même écriture laisse le processus vivant. Sous runtime : `UPDATE processes SET risk_framework_id = NULL, deleted_at = now()` (accepté, le processus est supprimé) puis `UPDATE processes SET deleted_at = NULL` (le trigger ne surveille pas `deleted_at`) ⇒ processus vivant détaché sans approbation (vérifié). La même séquence permet de faire revivre un processus rattaché à un Dispositif archivé entre-temps. Aucun chemin applicatif ne restaure un processus aujourd'hui : c'est la limite connue d'une écriture forgée sous runtime. Durcissement à coût nul : ajouter `deleted_at` au `UPDATE OF` du trigger et refuser `deleted_at` non NULL → NULL (ou exiger alors un Dispositif ouvert).

### SEC-B13-02 — INFO (A06)
Comme A06 l'a signalé, le provisionnement n'est pas atomique. Trois appels parallèles = 201, 409, 409, et deux échelles DRAFT orphelines (créées avant que l'index unique sur le nom du Dispositif refuse). Même chose après un échec partiel ou après un renommage, qui libère le nom. Sans effet de sécurité : l'échelle est en DRAFT, rattachée à rien, et le RM ne peut pas l'éditer. Recommandation simple : une transaction par modèle (échelle + Dispositif), ou réutiliser une échelle DRAFT orpheline du même nom.

### SEC-B13-03 — INFO (A06)
L'ordre inverse de R1 (l'archivage prend le Dispositif `FOR UPDATE` d'abord, une soumission tient déjà la version `FOR UPDATE` puis insère sa demande) se termine en interblocage détecté par PostgreSQL (40P01) : l'une des deux transactions est annulée et l'utilisateur reçoit un 500. L'état reste cohérent (rien de partiel, tout est transactionnel). Possible correctif : dans `archiveFramework`, verrouiller les versions avant de lire les demandes, ou mapper 40P01 en 409 « réessayez ».
