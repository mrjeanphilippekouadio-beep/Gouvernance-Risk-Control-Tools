**I-D9 contournable par un RM qui cumule administrateur, et `askedOn` sans borne basse.**

- Précondition : l'unique RM détient aussi un droit d'administrateur (`user.create` + `role.assign`, cumul autorisé et marqué q63).

Elle ne regarde ni qui a accordé ce droit, ni quand.

L'impact reste borné : une seule activation, avec les valeurs du contrat (q98).

Option PO, car elle touche q103 : notifier l'administrateur nommé (`RISK_FRAMEWORK_BOOTSTRAP_NOTICE`), seul témoin capable de contester une déclaration fabriquée.

### F-B6d-04 — LOW 1,9 (CVSS:3.1/AV:N/AC:H/PR:H/UI:N/S:U/C:N/I:N/A:L), CONFIRMED (PoC à fenêtre élargie), owner A07 + A06

**`SELECT … FROM tenants FOR UPDATE` dans le trigger et dans `recordBootstrapDecision`.**

- Montée de verrou : l'`INSERT INTO user_roles` prend d'abord `FOR KEY SHARE` sur la ligne `tenants` (contrôle FK `user_roles_tenant_id_fkey`, trigger RI déclenché avant `user_roles_bootstrap_end_mark_insert`), puis le trigger demande `FOR UPDATE`. Deux affectations concurrentes à des groupes fixes **différents** (le verrou `roles FOR UPDATE` de `assignToUser` ne les sérialise pas) peuvent chacune tenir `KEY SHARE` et attendre l'autre. PoC (`dl.sql`, `KEY SHARE` explicite pour élargir la fenêtre) : `ERROR: deadlock detected … SELECT 1 FROM tenants WHERE id = t FOR UPDATE`. En réel, la fenêtre est de quelques microsecondes. L'échec est sûr : une affectation est annulée, rejouable, et le marqueur reste cohérent.
- Disponibilité : pendant toute la transaction BOOTSTRAP, `FOR UPDATE` bloque **toute insertion** dans les tables qui ont une FK vers `tenants` pour ce tenant (KEY SHARE incompatible). La durée est courte.
- Correctif proposé : `FOR NO KEY UPDATE` aux deux endroits. Les deux demandes restent mutuellement exclusives (NO KEY UPDATE contre NO KEY UPDATE), elles sont compatibles avec `KEY SHARE`, et l'`UPDATE tenants SET risk_framework_bootstrap_ended_at` (colonne non clé) prend déjà ce mode. Rejouer ensuite les courses 1 et 2 ci-dessus : le comportement attendu est inchangé.
