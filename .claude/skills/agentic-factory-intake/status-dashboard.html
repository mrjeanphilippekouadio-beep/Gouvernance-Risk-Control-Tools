Points de vigilance

Un seul environnement. La base Neon utilisée en développement est la base réelle — aucune séparation dev/prod aujourd'hui.
Rien n'est déployé. La CI construit et teste, mais aucun Cloud Run n'est actif — l'app ne tourne qu'en local.
Secrets en clair localement. Le token Telegram et DATABASE_URL vivent dans un .env non commité — à migrer vers un gestionnaire de secrets avant toute mise en production.
Pas d'onboarding self-service. Ajouter un utilisateur autorisé demande aujourd'hui un INSERT SQL manuel dans users.
Divergence non tranchée. Le modèle LLM de l'agent DevOps (A09) diffère entre la feuille Config et la feuille Model Registry du classeur ACF.
5 agents ACF sans prompt source. A01 (Intake, actif), A11, A17, A19, A20 référencés dans la hiérarchie mais absents de la feuille System Prompts.

Prochaines étapes recommandées

  1. Décider et déployer un environnement de productionCloud Run, séparé de la base de développement, secrets en Secret Manager.
  2. Construire l'onboarding utilisateurACT-090 à 093 — sortir de l'ajout manuel en base pour whitelister un nouvel utilisateur.
  3. Rendre les permissions éditablesACT-116/118 — une vraie matrice IAM en base plutôt qu'une énumération TypeScript figée.
  4. Reprendre le backlog métierRiskEvaluation, KRI et RiskAppetite sont les briques les plus proches du cœur risque déjà construit.
  5. Revue de sécurité/security-review sur l'ensemble avant d'ouvrir l'accès à davantage d'utilisateurs.
  6. Décider de la suite TelegramPhase B2 (transcription vocale, fournisseur à choisir) et Phase C (piloter GRC Tools depuis Telegram), ou s'arrêter à B1.
Méthodologie : couverture calculée à partir des 142 actions du backlog ACF (.claude/backlog/grc-actions.yaml), pondérée par domaine. Les pourcentages par module reflètent une estimation raisonnée du code existant, pas une mesure automatisée — à recalibrer si la définition d'une action change.
