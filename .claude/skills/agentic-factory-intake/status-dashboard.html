Points de vigilance

Revue de sécurité effectuée sur le code déjà en production. 6 vulnérabilités réelles corrigées (maker-checker contournable sur l'exécution de contrôle, surcharge client de champs sensibles, permissions héritées non filtrées, suppression Drive définitive au lieu d'une corbeille…) — suite couverte par 16 tests de régression dédiés.
Onboarding partiellement outillé. Un admin peut désormais créer un utilisateur via POST /users (UserManagement) au lieu d'un INSERT SQL manuel. Reste : invitation / whitelist SSO en libre-service (ACT-090-092).
KRI a maintenant un vrai ciblage d'alerte possible. Risk.ownerId existe depuis RiskOwnership — reste à câbler l'alerte KRI dessus (elle notifie encore de façon best-effort, sans journal persistant).
Cartography.ownerId n'est pas encore câblé. Le module a été construit en parallèle de RiskOwnership et rejette explicitement ce filtre pour l'instant (ValidationError volontaire plutôt qu'un no-op silencieux) — petit patch de suivi maintenant que Risk.ownerId existe.
ActionPlan.ACT-193 (auto-escalade) n'a pas de déclencheur périodique. Aucun scheduler/cron n'existe dans ce backend — le statut "En retard" est calculé à la lecture (comme KRI), et la notification d'escalade n'est appelée qu'à des points précis (démarrage d'une action déjà en retard, appel manuel), jamais en tâche de fond.
RiskEvaluation ne capture toujours pas de score de vélocité. Bloque la taille des bulles dans Cartography — décision à prendre sur qui possède ce champ.
Un seul environnement. La base Neon utilisée en développement est la base réelle — aucune séparation dev/prod aujourd'hui.
Rien n'est déployé. La CI construit et teste, mais aucun Cloud Run n'est actif — l'app ne tourne qu'en local.
Secrets en clair localement. Le token Telegram et DATABASE_URL vivent dans un .env non commité — à migrer vers un gestionnaire de secrets avant toute mise en production.
RiskEvaluation duplique sous-catégorie/entité depuis Risk. Risk n'a pas encore de colonne subCategory/entity canonique ; l'évaluation les capture en snapshot à la création (cohérent avec le legacy Apps Script) — à trancher si ces champs doivent migrer sur Risk.
Divergence non tranchée. Le modèle LLM de l'agent DevOps (A09) diffère entre la feuille Config et la feuille Model Registry du classeur ACF.
5 agents ACF sans prompt source. A01 (Intake, actif), A11, A17, A19, A20 référencés dans la hiérarchie mais absents de la feuille System Prompts.
9 modules n'ont pas encore d'interface frontend. KPI, RiskAppetite, RatingScale, UserManagement, RiskEvaluation, KRI, RiskOwnership, ActionPlan et Cartography sont utilisables via API seulement — le frontend reste sur Risk/Admin/Feedback.

Prochaines étapes recommandées

  1. Câbler le filtre Risk Owner de CartographyPetit patch : Risk.ownerId existe désormais (RiskOwnership) — il ne reste qu'à connecter le filtre déjà prévu côté Cartography.
  2. Construire l'interface frontend des 9 nouveaux modulesKPI, RiskAppetite, RatingScale, UserManagement, RiskEvaluation, KRI, RiskOwnership, ActionPlan, Cartography n'existent qu'en API — le design system livré (Table, FormField, StatusBadge, Button) est prêt à les recevoir.
  3. Reprendre le reste du backlogDashboard, Reporting et Config sont les briques restantes les plus transverses ; Governance/Notification/JournalGlobal restent à cadrer.
  4. Décider et déployer un environnement de productionCloud Run, séparé de la base de développement, secrets en Secret Manager.
  5. Achever l'onboarding utilisateur en libre-serviceACT-090 à 092 — whitelist / invitation SSO, au-delà de la création admin déjà livrée.
  6. Rendre les permissions éditablesACT-116/118 — une vraie matrice IAM en base plutôt qu'une énumération TypeScript figée.
  7. Décider de la suite TelegramPhase B2 (transcription vocale, fournisseur à choisir) et Phase C (piloter GRC Tools depuis Telegram), ou s'arrêter à B1.
